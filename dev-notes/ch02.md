## 阶段 1：需求定稿与文档核对

**用户关键原话**
> 我要给现有的客服系统装上查数据的能力,用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身,用户在聊天页问一句就能触发。

**关键产出**
- 用 Context7 核对后确认：
  - SQLAlchemy 2.1.8：`DeclarativeBase` + `Mapped` + `mapped_column` 声明模型，`sessionmaker` 管理会话；
  - LangChain 1.8：`@tool(args_schema=...)` 定义参数 Schema，`bind_tools` 绑定，流式 `AIMessageChunk` 相加可聚合 `tool_calls`，回灌用 `ToolMessage(tool_call_id=...)`。
- 定稿流程：`model_with_tools.astream` → 聚合工具调用 → 推送 `tool` 状态帧 → 执行单工具 → `ToolMessage` 回灌 → 第二次 `astream` 输出最终答案。

**拒绝与纠偏**
- 拒绝做多轮 Agent Loop：本章明确只执行第一个工具、一次收敛。

**翻车与返工**
- 暂无。

**关键产出**
- [mock_api.py](file:///e:/03_Project/BusiHelp/app/tools/mock_api.py)：`query_order` / `query_product` / `query_logistics`，按单号做确定性随机，结果稳定可复现。

**拒绝与纠偏**

## 阶段 4：工具链接入 SSE 对话与落库

**用户关键原话**
> 工具链接进现有客服聊天入口:那个 SSE 流式聊天页……最终回答仍逐 token 流式吐出,工具执行那一段先推个状态帧;聊天记录(含工具调用与结果)落 conversations/messages 表。

**关键产出**
- [chat_service.py](file:///e:/03_Project/BusiHelp/app/chat_service.py)：首轮流式聚合工具调用；命中后推送 `tool/start`、执行、推送 `tool/done`；保存 assistant(`tool_calls`) 与 tool(`tool_call_id`) 消息；用 `ToolMessage` 回灌后二次流式输出最终答案。
- 无工具调用时直接流式输出，行为与 ch01 一致；历史只回放 user / 最终 assistant（跳过工具中间消息），避免孤立 tool 消息。
- [main.py](file:///e:/03_Project/BusiHelp/app/main.py)：`/chat/stream` 转接编排器；`/health` 增加 DB 探活；保留 `/extract` 与静态页。
- 实测落库：conversations 5、messages 18、tickets 2；tool 消息带 `tool_call_id`，assistant 工具消息带 JSON `tool_calls`。

**拒绝与纠偏**
- 拒绝把工具执行做成吞掉异常的静默分支：失败也回灌 `{"error": ...}`，让模型向用户解释。

**翻车与返工**
- 多轮回归发现：工具轮之后的追问会丢失上下文，模型反过来追问订单号。定位为 MySQL JSON 列把 Python `None` 存成了 JSON `null`，导致 `tool_calls IS NULL` 过滤永远不命中，历史被整体跳过。
- 返工：`JSON(none_as_null=True)` 让空值落 SQL NULL；`load_history` 去掉 SQL 层 JSON 判断，改为在 Python 侧跳过带 `tool_calls` 的行，兼容历史脏数据。重建会话复测：第二轮成功沿用订单 1001 并再次调用 `query_logistics` 作答。
